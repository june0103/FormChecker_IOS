# 판정 엔진 포팅 명세 (`:pose-engine` → `PoseEngine`)

> **정본은 이 문서가 아니라 Android 코드다.** 값이 다르면 Android `79ef0bb`를 따른다.
> 이 문서는 **무엇을 어떤 순서로 옮기고, 어디서 틀리는지**를 알려주는 지도다.
> 작성일 2026-11-20

---

## 0. 원칙

1. **알고리즘을 "개선"하지 않는다.** 더 좋아 보이는 방법이 떠올라도 그대로 옮긴다.
   이 코드의 숫자 대부분은 실측 15세션을 거쳐 나왔고, 중간에 **버려진 접근이 여럿 있다**
   (무릎 각도 깊이 판정, 무릎폭 배수 valgus, 프레임 단위 무릎–발끝). 다시 만들면 그 길을 다시 간다.
2. **판정 불가는 `nil`이다.** `0`이나 `false`로 바꾸지 않는다.
3. **임계값에는 출처 등급을 함께 옮긴다.** `DATA_DERIVED` / `DEFINITION` / `PROVISIONAL`.
4. **테스트를 먼저 옮긴다.** Android 테스트 28개 파일이 이식 정확도의 유일한 증거다.

## 2. 키포인트 — Halpe26

```
0 NOSE          7  LEFT_ELBOW     14 RIGHT_KNEE     21 RIGHT_BIG_TOE
1 LEFT_EYE      8  RIGHT_ELBOW    15 LEFT_ANKLE     22 LEFT_SMALL_TOE
2 RIGHT_EYE     9  LEFT_WRIST     16 RIGHT_ANKLE    23 RIGHT_SMALL_TOE
3 LEFT_EAR      10 RIGHT_WRIST    17 HEAD           24 LEFT_HEEL
4 RIGHT_EAR     11 LEFT_HIP       18 NECK           25 RIGHT_HEEL
5 LEFT_SHOULDER 12 RIGHT_HIP      19 HIP_CENTER
6 RIGHT_SHOULDER13 LEFT_KNEE      20 LEFT_BIG_TOE
```

- 0~16은 COCO17과 같다.
- **17·18·19(HEAD/NECK/HIP_CENTER)는 표시하지 않는다** — 다른 점과 겹친다.
- **20~25(발 6개)가 이 모델을 쓰는 이유다.** 뒤꿈치 들림·무릎–발끝 판정이 여기에 달려 있다.
- 좌표는 **letterbox를 걷어낸 원본 프레임 기준 0~1**.
- `MIN_CONFIDENCE = 0.3` 미만은 **에러가 아니라 정상 스킵**이다.

## 3. 추론 (`RTMPoseEngine`)

### 3.1 모델 입출력 (파일에서 확인된 값)

```
INPUT  [1, 256, 192, 3] FLOAT32   RGB 0~255 raw        ← 정규화는 모델 내부에 포함
OUTPUT [1, 26, 384]     FLOAT32   simcc_x (192 × 2.0)
OUTPUT [1, 26, 512]     FLOAT32   simcc_y (256 × 2.0)
```

- 입력 크기 **W 192 × H 256**.
- 🔴 **÷255 하지 않는다.** 이중 정규화가 되면 키포인트가 조용히 엉뚱한 곳에 찍힌다.
- 출력 텐서 순서는 **이름이 아니라 마지막 차원 크기로 판별**한다 (x bin 384 < y bin 512).
  뒤바뀌면 스켈레톤이 90도 돌아간 것처럼 나온다.

### 3.2 디코딩

1. 키포인트별로 `simcc_x`·`simcc_y` 각각의 **argmax** 인덱스를 찾는다.
2. `index / 2.0` → 모델 입력 픽셀 좌표.
3. 입력 크기로 나눠 0~1 정규화.
4. `LetterboxTransform.inverse()`로 패딩을 걷어낸다.
5. confidence = **두 축 최댓값 중 작은 쪽** (`min(xMax, yMax)`).

### 3.3 letterbox

```
scale      = min(targetW / srcW, targetH / srcH)
scaledW    = round(srcW * scale)   (≤ targetW)
scaledH    = round(srcH * scale)   (≤ targetH)
padLeft    = (targetW - scaledW) / 2        ← 정수 나눗셈
padTop     = (targetH - scaledH) / 2
forward(x,y) = ((padLeft + x*scaledW)/targetW, (padTop + y*scaledH)/targetH)
inverse(x,y) = ((x*targetW - padLeft)/scaledW, (y*targetH - padTop)/scaledH)
```

- 패딩은 **검정(0,0,0)**.
- 프리뷰가 3:4라 **실제 패딩은 0**이다. 그래도 변환은 유지한다 — 기기마다 실제 해상도가 다를 수 있다.
- 변환 객체는 **프레임 크기가 바뀔 때만** 새로 만든다 (캐시).

### 3.4 iOS 전처리 (Android과 달라지는 유일한 구간)

| 단계 | 할 일 |
|---|---|
| 1 | `CVPixelBuffer`를 잠그고 베이스 주소를 얻는다 (`kCVPixelFormatType_32BGRA`) |
| 2 | 🔴 **B·G·R·A 순서를 R·G·B로 바꾼다** — Android는 RGBA였다 |
| 3 | 비율 유지 축소 (`vImageScale_ARGB8888` 권장). **보간 방식을 Android와 맞춘다** |
| 4 | 검정 배경 192×256 버퍼 가운데에 복사 |
| 5 | float32 배열에 R,G,B 순으로 채운다 (0~255 그대로) |
| 6 | **벌크로 한 번에** `Data`/`UnsafeMutableBufferPointer`에 쓴다 (한 값씩 쓰면 Android 실측 기준 23배 느리다) |
| 7 | 추론 실패는 **`nil` 반환 + 드롭 카운트**. 세션은 죽지 않는다 |

버퍼(입력 픽셀 배열, float 배열, 변환 객체)는 **프레임마다 새로 만들지 않고 재사용한다.**

## 4. 프레임 특징 (`FrameFeatures`)

모든 정규화 특징은 **기준선(`StandingCalibration`)을 분모로 쓴다.** 기준선이 없으면
그 특징은 `nil`이고, **각도로 대체되지 않는다.**

| 특징 | 정의 | 쓰이는 곳 |
|---|---|---|
| `depthRatio` | `(hip.y − knee.y) / legLength` | 깊이 (기준선 있을 때) |
| `shinDepthRatio` | `(hip.y − knee.y) / (ankle.y − knee.y)` | 깊이 (기준선 없을 때) · 각종 게이트 |
| `trunkLean` | 어깨–엉덩이 선의 수직 대비 각도 | 상체 숙임 |
| `heelRise` | 기립 기준 대비 뒤꿈치 상승량(정강이 정규화) | 뒤꿈치 들림 |
| `kneeOverToe` | 무릎이 발끝을 넘은 정도. 앞쪽은 `sign(발끝.x − 뒤꿈치.x)`로 **발이 스스로 가리킨다** | 무릎–발끝 |
| `footTibiaRatio` | `발 길이 / 정강이` | **발 가시성 게이트** |
| `ankleSpread` | 발목 간격 | 무릎–발끝 게이트 |
| `left/rightKneeToeDeviation` | `(무릎.x − 발끝.x) / 발목 간격`. 양수 = 내측 | 무릎 모임/벌어짐 |
| `hipShiftRatio` | 좌우 골반 쏠림 | 좌우 쏠림 |

> ⚠ **분모를 의심할 것.** 측면에서 발 길이·어깨폭·힙폭은 원근으로 압축되고,
> 발목 간격은 두 발이 겹치면 무너진다. 이 프로젝트에서 정규화 실패가 반복해서 나왔다.

| 값 | 단위 | 의미 |
|---|---|---|
| `emaTimeConstantMs` | **120.0 ms** | 지수이동평균 시정수 |

## 6. rep 상태머신

```
IDLE ──(각도 ≥ 155°)──▶ STANDING ──(각도 < 145°)──▶ DESCENDING
                            ▲                            │
                            │                     (각도 < 130°)
                            │                            ▼
                            └──(각도 ≥ 155°)── ASCENDING ◀─▶ BOTTOM
                                               (각도 ≥ 130°)
```

| 임계값 | 값 | 출처 |
|---|---|---|
| `standingEnterAngle` | **155°** | PROVISIONAL |
| `standingExitAngle` | **145°** | PROVISIONAL |
| `repBottomAngle` | **130°** | PROVISIONAL |
| `minHoldMs` | **100 ms** | PROVISIONAL — 상태 전이 전 유지 시간 |
| `minRepDurationMs` | **700 ms** | PROVISIONAL — 이보다 빠르면 `TOO_FAST`로 버린다 |
| `maxRepDurationMs` | **15,000 ms** | PROVISIONAL — 넘으면 `TIMEOUT` |
| `maxMissingMs` | **1,000 ms** | PROVISIONAL — 포즈 소실 허용 시간 |

**중단 사유**: `NOT_DEEP_ENOUGH` / `TOO_FAST` / `TIMEOUT` / `POSE_LOST`.
`POSE_LOST`는 `IDLE`로, 나머지는 `STANDING`으로 돌아간다.

🔴 **카운팅 임계값과 자세 임계값은 서로 참조하지 않는다.** 설계 초판은 BOTTOM 진입을
`< 100°`, 깊이 부족을 `≥ 120°`로 뒀는데 **두 조건이 동시에 참일 수 없어** 깊이 부족 경고가
영원히 안 났다. 분리가 그 해법이다.

**얕은 rep도 센다.** 세지 않으면 사용자에게는 카운터가 멈춘 것처럼 보인다 — 세고, 경고한다.

**최저점은 중앙값 각도가 가장 작은 프레임**으로 잡는다(`updateBottomCandidate`).

## 7. 기준 자세 (`StandingCalibration`)

| 항목 | 값 |
|---|---|
| 필요 키포인트 | 어깨·엉덩이·무릎·발목 **좌우 8개 전부** |
| 최소 confidence | **0.5** (프레임 판정의 0.3보다 높다) |
| 최소 프레임 | **20** |
| 다리 길이 하한 | **0.15** (정규화 좌표) |
| 떨림(jitter) 상한 | **0.01** |
| 기립 무릎 굴곡 상한 | **20°** |

**산출물**: 대퇴·정강이 길이, 힙·어깨 너비, 몸통 길이, 발 길이, 기립 무릎/발목 각도,
기립 힙 Y, 기립 뒤꿈치 Y, 좌우 뒤꿈치 기준 오프셋.

**실패 사유와 문구**

| 사유 | 문구 | 막는가 |
|---|---|---|
| `TOO_FEW_FRAMES` | 자세를 유지한 시간이 짧았어요 — 다시 해볼까요? | ✅ |
| `SUBJECT_TOO_SMALL` | 카메라를 더 가까이 두세요 — 머리부터 발까지 화면에 크게 담겨야 해요 | ✅ |
| `UNSTABLE` | 움직임이 있었어요 — 잠깐 그대로 서 계세요 | ✅ |
| `NOT_STANDING_STRAIGHT` | 무릎을 곧게 펴고 서 주세요 | ✅ |
| `AMBIGUOUS_VIEW` | 카메라를 똑바로 마주 보거나 옆으로 서 주세요 (지금은 비스듬해요) | ✅ |
| `FOOT_NOT_VISIBLE` | 발이 보이지 않습니다 — 발 관련 항목은 기록되지 않습니다 | ❌ |

**활성측(`nearerSide`)** — 힙·무릎·발목 평균 confidence가 높은 쪽. 측면 판정은 이 한쪽만 본다.

## 8. 촬영 방향 판별

```
ratio = 어깨 너비 / 몸통 길이
ratio ≥ 0.55 → FRONT
ratio ≤ 0.30 → SIDE
그 사이       → AMBIGUOUS (측정을 막는다)
몸통 길이 < 0.05 → nil (판정 불가)
```

| 임계값 | 값 | 출처 |
|---|---|---|
| `frontRatio` | **0.55** | DATA_DERIVED — 정면 세션 중앙값 0.675~0.731 |
| `sideRatio` | **0.30** | DATA_DERIVED — 측면 세션 중앙값 0.058~0.105 |
| `minTorsoLength` | **0.05** | PROVISIONAL |

🔴 **프레임 단위로 쓰지 않는다.** 세션 단위 다수결은 15/15 전부 맞았지만,
프레임 단위로는 양쪽 0.5%가 반대로 읽히고 그게 두 세션에 몰려 있다 —
rep 한가운데서 판정이 뒤집힌다.

👉 기준 자세 측정 창의 프레임들을 모아 **최빈값**을 취하고, 그 세션 동안 **고정**한다.

|---|---|---|---|
| `SHALLOW_DEPTH` | DEPTH | 측면 | **rep** |
| `EXCESSIVE_LEAN` | TORSO_LEAN | 측면 | 프레임 |
| `HEEL_RISE` | HEEL_LIFT | 측면 | 프레임 |
| `KNEE_PAST_TOE` | KNEE_OVER_TOE | 측면 | **rep** |
| `KNEE_VALGUS` | KNEE_ALIGNMENT | 정면 | 프레임 |
| `KNEE_FLARED` | KNEE_ALIGNMENT | 정면 | 프레임 |
| `HIP_SHIFT` | SYMMETRY | 정면 | 프레임 |

### 10.1 프레임 판정 (`warningsOf`)

```
heelRise  > 0.18              → HEEL_RISE
trunkLean > 45°               → EXCESSIVE_LEAN
|hipShift| > 0.10             → HIP_SHIFT
kneeToeDeviation >  0.10      → KNEE_VALGUS
kneeToeDeviation < −0.10      → KNEE_FLARED
```

### 10.2 rep 판정 (`RepWarnings.of`)

```
shallow = (depth == SHALLOW) && !heelLifted        ← 🔴 배제 규칙
kneePastToe = rep 중앙값 > 0                        ← 중앙값, 최댓값 아님
경고 = 프레임 경고 ∪ {SHALLOW_DEPTH if shallow} ∪ {KNEE_PAST_TOE if kneePastToe}
```

🔴 **rep 단위 2종은 분석기가 프레임 경고로 내보내지 않는다.** 하강은
`STANDING → SHALLOW → PARALLEL`을 지나므로, 프레임마다 말하면 **아직 내려가는 중인 사람에게
"덜 앉았다"** 고 하는 것이 된다.

🔴 **뒤꿈치가 뜨면 깊이 부족을 말하지 않는다.** 올바른 깊이는 "뒤꿈치가 뜨지 않는 범위까지"라
둘이 함께 뜨면 서로 반대인 지시가 된다.

🔵 **뒤꿈치 들림과 무릎–발끝은 서로 배제하지 않는다.** 원인도 지시도 같은 방향이다.

### 10.3 게이트

| 판정 | 게이트 |
|---|---|
| `HEEL_RISE` | 촬영 측면 **and** `footTibiaRatio ≥ 0.45` |
| `KNEE_PAST_TOE` | 위와 같은 발 가시성 게이트 **and** `shinDepthRatio ≥ −0.8` |
| `KNEE_VALGUS`/`FLARED` | 촬영 정면 **and** `shinDepthRatio ≥ −0.8` **and** `ankleSpread ≥ 0.04` |
| 깊이 | 기준선 있으면 `depthRatio`, 없으면 `shinDepthRatio`. **둘 다 없으면 `nil`** |

### 10.4 깊이 판정

```
기준선 있음:  ratio ≤ −0.40 → STANDING
              ratio ≥ +0.03 → DEEP
              ratio ≥ −0.03 → PARALLEL        (완화 시 −0.10)
              그 외          → SHALLOW

기준선 없음:  shin ≤ −0.83 → STANDING
              shin ≥ +0.062 → DEEP
              shin ≥ −0.062 → PARALLEL        (완화 시 −0.208)
              그 외          → SHALLOW
```

🔴 **무릎 각도로 깊이를 판정하지 않는다.** 각도 경로는 측면 3세션에서 깊이비 경로와
45~67%만 일치했고, 불일치가 전부 한 방향(SHALLOW를 DEEP으로)이라 **깊이 부족 경고가 한 번도
발화하지 않았다.** 각도는 깊이의 대리 변수가 될 수 없다 — 정강이 기울기가 교란한다.

## 11. 준비 자세 5종 (`ReadyPosture`)

| 항목 | 막는 사유 |
|---|---|
| 방향 | `TURN_TO_FRONT` · `TURN_TO_SIDE` · `FACE_SQUARELY` |
| 무릎 펴기 | `KNEES_BENT` |
| 발 간격 | `STANCE_TOO_NARROW` · `STANCE_TOO_WIDE` ⚠ **막는 판정 중 유일하게 허용폭이 PROVISIONAL** |
| 발끝 방향 | `TOES_INWARD` |
| 좌우 균형 | `WEIGHT_ON_ONE_SIDE` |

- **전부 막는 항목(blocking)이다.** 오탐하면 사용자가 앱을 **아예 쓸 수 없다**.
- 발 간격은 `발목 간격 / 어깨 너비`이고 기준점이 1.0이다.
- 최근 **15프레임**으로 실시간 갱신한다.
- **못 본 항목은 통과로 본다** — 안 그러면 측면 촬영으로는 영원히 시작할 수 없다.
- 결과를 **저장하지 않는다**.
- ⚠ 실측 12세션 중 2개가 현재 기준으로는 시작하지 못한다. "시작이 안 된다"는 신고가 오면 **여기를 먼저 본다**.

## 12. 피드백 hold

- 항목당 **2초**. 최저점 경고를 다 올라온 뒤 읽을 수 있어야 한다(상승 p95 1,171ms).
- **항목마다 다르게 두지 않는다.**
- 한 항목에 **하나만** 남긴다.
- 정렬은 **도착 순(새 것이 맨 위)**. 우선순위 순이 아니다.
- 같은 프레임에 함께 나면 그때만 선언 순서로 가른다.

## 13. 세션 리포트 (`SessionReporter`)

1. **점수를 내지 않는다.** 항목별 "몇 번 나왔는가"를 세고 **잦은 것부터**.
2. **"몇 % 이상이면 습관"을 정하지 않는다.** 횟수를 그대로 적는다.
3. **분모는 그 항목을 판정한 rep 수**다. 전체 rep이 아니다.
4. **구간을 말한다** — 하강/최저점/상승 중 **과반**인 구간. 과반이 없으면 "동작 내내".
   구간은 **rep 수로 센다**(프레임 수가 아니다 — 긴 구간이 항상 이긴다).
5. **못 본 것을 반드시 말한다** — 이유는 `CAMERA_ANGLE` 또는 `NO_JUDGED_REP`.
6. 좌우 지목은 한쪽이 **75% 이상**일 때만. 아니면 쪽만 빠지고 경고는 남는다.
7. 문제가 없을 때 **"자세가 좋았다"고 쓰지 않는다** — "경고가 난 rep이 없다"는 사실만.

## 14. 칼로리

```
RMR(kcal/일) = 10×체중(kg) + 6.25×키(cm) − 5×나이 + (남성 +5 / 여성 −161)   ← Mifflin-St Jeor
1회당 kcal   = 5.0 METs × (RMR / 1440) / 10회
```

- 키·몸무게가 없으면 **계산하지 않는다**. 나이·성별이 없으면 30세·남성으로 **가정하고 밝힌다**.
- **깊이를 보지 않는다** (원 논문이 반복 빈도 회귀로 정의).
- 70kg·170cm·25세 남성에서 1회당 **0.570 kcal** — Nakagata et al. 2022(JSCR) 0.50±0.14의 95% 신뢰구간 안.
  ⚠ **테스트가 이 일치를 붙들고 있다. 상수를 손대면 깨진다.**
- 저장하지 않고 **볼 때마다 계산**한다.

### 이식 중 **드러난 것**

**`CountingThresholds`의 불변식이 Swift 포팅에서 한 번 빠졌다.** Kotlin `data class`는
`init`의 `require`가 `copy()`에서도 다시 돌지만, Swift `struct`의 `var` 프로퍼티는 생성 후
아무 값으로나 바꿀 수 있어 **히스테리시스가 깨진 설정이 만들어질 수 있었다.**
프로퍼티를 `let`으로 바꾸고 던지는 `init`을 두어 막았다 — 구조가 다르면 같은 불변식도
다른 방법으로 지켜야 한다는 예다.

> 👉 **화면을 만들기 전에 통과해야 하는 게이트는 이것으로 닫혔다.**
