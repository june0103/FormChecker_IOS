# Phase 0 결과 — 키포인트 동등성

> **결론: 게이트 통과.** 최근접 샘플링을 쓰면 iOS가 Android와 **사실상 같은 키포인트**를 낸다
> (최대 좌표차 **7.16 × 10⁻⁷**, 게이트 0.01의 1만 4천분의 1). 단, 보간 방식을 잘못 고르면 **0.42까지 벌어진다.**
> 측정일 2026-11-20 · Android 기준 `79ef0bb`

---

## 1. 무엇을 쟀나

같은 PNG 4장을 양 플랫폼의 **프로덕션 추론 경로**에 넣고 키포인트 26개를 비교했다.

| 이미지 | 크기 | 무엇을 고립시키나 |
|---|---|---|
| `squat_bottom_192x256` | 192×256 | 리사이즈·패딩 없음 → **색 순서와 정규화만** |
| `squat_bottom_480x640` | 480×640 | 리사이즈만 (패딩 0) → **실제 카메라 경로** |
| `squat_bottom_500x500` | 500×500 | 리사이즈 + 상하 패딩 32px |
| `standing_480x640` | 480×640 | 기립 자세 (다른 포즈에서도 같은지) |

이미지는 이 프로젝트의 동작 예시 GIF(`squat_form_example.gif`)에서 뽑았다. 알파 채널을
제거(`rgb24`)해 프리멀티플라이 때문에 두 플랫폼이 다른 픽셀을 보는 경우를 원천 차단했고,
양쪽이 **sha256이 같은 파일**을 읽는다.

**경로**
- Android: `RtmPoseEngine.analyze(Bitmap)` — 앱이 쓰는 그 함수. 에뮬레이터 `portfolio_pixel8`(API 36, arm64)
- iOS: `RTMPoseEngine.analyze(frame:)` — 시뮬레이터 iPhone 17
- 모델: **같은 파일** `rtmpose_s_halpe26_256x192_f16.tflite` (11,450,804 B)

## 2. 결과

좌표는 0~1 정규화. 게이트는 **0.01** (480px 폭에서 약 4.8px).

| 리샘플링 | 이미지 | 최대 좌표차 | 평균 | 완전일치 | 판정 |
|---|---|---|---|---|---|
| **nearest** | 192×256 | **0.000001** | 0.000000 | 22/26 | ✅ |
| **nearest** | 480×640 | **0.000001** | 0.000000 | 21/26 | ✅ |
| **nearest** | 500×500 | **0.000001** | 0.000000 | 22/26 | ✅ |
| **nearest** | standing | **0.000001** | 0.000000 | 22/26 | ✅ |
| bilinear | 192×256 | 0.000001 | 0.000000 | 22/26 | ✅ |
| bilinear | 480×640 | 0.052230 | 0.007149 | 0/26 | ❌ |
| bilinear | 500×500 | **0.416699** | 0.032376 | 1/26 | ❌ |
| bilinear | standing | 0.088563 | 0.006285 | 4/26 | ❌ |

표의 0.000001은 CSV 소수점 6자리 표기의 한계다. Swift 쪽에서 직접 잰 **최악값은 7.16e-07**
(`standing_480x640` #18 NECK). **26개 중 21~22개는 비트 단위로 같다.**

판정 가능/불가 경계(confidence 0.3)를 넘나든 키포인트는 **0개**다.

## 3. 가장 중요한 발견 — Android는 **최근접 샘플링**을 한다

Android의 전처리는 이 한 줄이다.

```kotlin
inputCanvas.drawBitmap(frame, null, dstRect, null)   // paint = null
```

`paint`가 `null`이면 필터링 플래그가 꺼져 있어 **보간 없이** 축소한다. 480×640 → 192×256은
가로·세로 2.5배 축소인데, 그 과정에서 픽셀의 60%가 그냥 버려진다.

> iOS에서 "당연한" 선택은 `vImageScale_ARGB8888`이나 Core Graphics이고, 둘 다 **기본이
> 양선형 이상**이다. 그대로 갔다면 키포인트가 **최대 0.42** 벌어진 채로, 크래시도 경고도
> 없이 "조금 이상한 판정"만 남았을 것이다.

이것이 [03 문서 §4](03_AOS_iOS_구현차이.md)가 전처리를 🔴로 표시한 이유이고,
**화면을 만들기 전에 이 테스트를 먼저 한 이유**다.

### 어디가 어긋났나 (bilinear)

| 이미지 | 최악 키포인트 | 차이 |
|---|---|---|
| 500×500 | `RIGHT_WRIST` | 0.4167 — 팔이 겹쳐 보이는 자리라 argmax가 통째로 다른 봉우리로 넘어갔다 |
| 500×500 | `RIGHT_ELBOW` | 0.2514 |
| standing | `RIGHT_ELBOW` | 0.0886 |
| 480×640 | `LEFT_WRIST` | 0.0522 |

**하체는 상대적으로 덜 흔들렸다**(발·무릎·발목 0.004~0.016). 하지만 스쿼트 판정의
허용폭이 `kneeToeToleranceRatio = 0.10`, `hipShiftLimit = 0.10` 수준이라
**0.016은 허용폭의 16%**다. 조용히 먹고 들어가기에 충분한 크기다.

## 4. 함께 확인된 것

| 항목 | 결과 |
|---|---|
| 색 채널 | iOS의 PNG 디코딩은 **RGBA**(`noneSkipLast`). 원본 바이트를 그대로 썼다(다시 그리지 않음) |
| 정규화 | **÷255 하지 않는다**가 맞다. 했다면 키포인트가 전부 무너졌을 것 |
| letterbox | 500×500에서 상하 패딩 32px, `inverse()`로 걷어낸 뒤 좌표가 일치 |
| 패딩 색 | 검정(0,0,0) |
| 발 키포인트 | 뒤꿈치·엄지·새끼발가락 **6개 모두 confidence 0.45~0.74로 검출** — 이 모델을 쓰는 이유가 실제로 성립한다 |
| SimCC 디코딩 | 출력 텐서를 마지막 차원 크기로 판별(384 < 512)하는 규칙이 iOS에서도 맞았다 |

## 5. 아직 모르는 것 ⚠

이 게이트는 **"같은 비트맵 → 같은 키포인트"** 만 증명했다. 다음은 **미검증**이다.

1. **실기기** — 양쪽 다 에뮬레이터/시뮬레이터, 즉 호스트 CPU다.
   측정된 추론 시간(Android 16.9~26.9ms / iOS 9.6~23.3ms)은 **성능 근거가 아니다.**
   PRD §3.2의 성능 목표는 실기기로 다시 재야 한다.
2. **실제 카메라 경로** — 여기서 검증한 입력은 PNG(RGBA)다.
   `AVCaptureVideoDataOutput`의 **BGRA + 회전 + stride 패딩**은 아직 통과하지 않았다.
   (채널 순서 바꿈은 단위 테스트로만 고정돼 있다)
3. **영상 시퀀스** — 정지 이미지 4장뿐이다. 프레임 간 스무딩·상태머신은 Phase 1에서.
4. **판정 로직** — 아직 한 줄도 이식하지 않았다. 이 게이트는 그 **전제**를 확인한 것이다.
5. **Core ML / Metal delegate** — CPU 경로만 썼다. delegate를 켜면 수치가 달라질 수 있으므로
   **켜는 순간 이 게이트를 다시 돌려야 한다.**
