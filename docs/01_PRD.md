## 1. 제품 정의

카메라로 **스쿼트 횟수를 자동으로 세고**, 자세가 어긋나면 **화면과 소리로 알려주는**
온디바이스 앱. 네트워크 없이 100% 동작한다.

**한 줄 요약** — 집에서 혼자 스쿼트할 때, 세어 줄 사람과 봐 줄 사람을 폰이 대신한다.

### 1.1 해결하는 문제

1. **몇 개 했는지 세기 귀찮다** — 세다가 놓친다.
2. **자세가 맞는지 스스로 모른다** — 무릎이 말리는지, 충분히 앉았는지 알 수 없다.

### 1.2 사용 맥락 (설계를 지배하는 제약)

**폰을 세워두고 2~3m 떨어져서 쓴다.** 이 한 줄이 이 제품의 설계 대부분을 결정한다.

- 손이 폰에 닿지 않는다 → 운동 중 조작은 사실상 불가능. 시작 전에 모든 준비가 끝나야 한다.
- 글자가 작으면 안 읽힌다 → rep 숫자 96pt, 경고는 짧은 문장 한 줄.
- **소리가 주 피드백 채널이다** → 화면을 못 볼 수도 있다는 전제로 소리를 설계한다.
- 집, 저녁, 조명이 밝지 않다 → 다크 단일 테마 고정.

### 1.3 대상 사용자

| | |
|---|---|
| **주 사용자** | 집에서 혼자 맨몸 스쿼트를 하는 사람. 자세를 "배운 적 없는" 사람이 기본 가정이다 |
| **전제하지 않는 것** | 운동 용어(rep·패럴렐·valgus)를 안다는 것, 삼각대가 있다는 것, 전신 거울이 있다는 것 |
| **쓰지 않을 사람** | 헬스장에서 기구 운동을 하는 사람 (기구 가림·3D 깊이 문제로 이번 범위 밖) |

## 2. iOS 1.0의 목표

### 2.1 가장 중요한 목표 — **판정 동등성**

iOS의 목표는 "비슷한 앱"이 아니라 **같은 영상을 넣으면 같은 답이 나오는 앱**이다.

이유는 데이터다. Android의 임계값 전부는 **자체 수집 15세션**(정면 12 / 측면 3)으로
확정됐고, "같은 모델·같은 기기라 domain gap이 없다"는 것이 그 값을 믿는 근거였다.
iOS가 다른 전처리·다른 모델을 쓰면 **그 근거가 통째로 사라진다** — 임계값 15개를 처음부터
다시 재야 한다.

> 그래서 iOS 1.0은 "같은 `.tflite` 모델 · 같은 전처리 · 같은 임계값"을 1순위 제약으로 둔다.
> 성능을 위해 이것을 바꾸는 결정은 **임계값 재검증 비용을 함께 계산한 뒤에만** 한다.
> (선택지 비교는 [03 문서 §3](03_AOS_iOS_구현차이.md#3-추론-런타임))

### 2.2 기능 동등성 (feature parity)

Android에서 **지금 되는 것**이 iOS 1.0에서 전부 된다. 빠지는 것은 [§4.2](#42-범위-밖-out-of-scope)에 명시한다.

### 2.3 하지 않는 것

- **새 기능을 추가하지 않는다.** 스쿼트 외 종목, 세트 개념, 소셜, 구독 — 전부 아니다.
- **판정 로직을 "개선"하지 않는다.** iOS 이식 중에 떠오른 개선은 Android 저장소에 이슈로 남기고,
  두 플랫폼이 동시에 바뀌게 한다. 한쪽만 고치면 그 순간부터 두 앱이 다른 답을 낸다.

## 3. 성공 기준

> ⚠ 아래 수치 중 `[잠정]`은 **근거가 아직 없는 제안값**이다. 이 프로젝트의 규칙(근거 없는
> 숫자에 반드시 표시)을 문서에도 적용한다. 실측 후 이 표를 갱신한다.

### 3.1 반드시 통과해야 하는 것 (출시 게이트)

| # | 기준 | 측정 방법 | 목표 |
|---|---|---|---|
| G1 | **rep 카운팅 동등성** | 동일 녹화 영상 5개를 양 플랫폼 파이프라인에 주입 | 카운트 **완전 일치** |
| G2 | **키포인트 동등성** | 같은 프레임의 26개 키포인트 정규화 좌표 비교 | 평균 오차 ≤ **0.01** `[잠정]` |
| G3 | **판정 동등성** | rep별 경고 집합(7종) 비교 | 일치율 ≥ **95%** `[잠정]` |
| G4 | **오프라인 동작** | 비행기모드로 전 기능 사용 | 기능 저하 **0** |
| G5 | **세션 중단 복구** | 전화 수신·앱 전환·화면 잠금 중 운동 | 세션이 죽지 않고, 죽으면 기록이 남음 |

G1~G3은 **iOS에만 있는 요구사항**이다. Android에는 비교 대상이 없었다.

### 3.2 성능 목표

| 지표 | Android 실측 (Galaxy S24 Ultra) | iOS 목표 |
|---|---|---|
| 추론 p95 | 35.82 ms (CPU, GPU 실패) | **≤ 25 ms** `[잠정]` — Core ML/Metal delegate 기대치 |
| 프레임 파이프라인 p95 | 37.18 ms (30fps 예산 33ms 초과) | **≤ 33 ms** `[잠정]` |
| 분석 FPS | 약 27 fps | ≥ 25 fps `[잠정]` |
| 모델 로드 | 측정값 보유 | 콜드스타트 블로킹 **0** (백그라운드 로드) |

> Android는 **30fps를 못 맞춘다**는 것이 실측으로 확인된 상태다. iOS에서 Core ML delegate가
> 붙으면 이걸 넘길 가능성이 있지만, **가설이다.** Android에서 "GPU면 빨라질 것"이라는 같은
> 모양의 가설이 실측으로 반증된 전례가 있다 (`DelegateBenchmark`). **벤치마크 전에는 성능
> 개선을 설계 전제로 쓰지 않는다.**

### 3.3 품질 기준

- **단위 테스트 이식률 100%** — Android `:pose-engine` 테스트(28개 파일)가 Swift로 전부 넘어오고 통과한다.
  이 테스트들이 §2.1의 판정 동등성을 코드 레벨에서 붙든다.
- 크래시 프리 세션 ≥ 99.5% `[잠정]`
- 카메라 권한 거부·모델 로드 실패·포즈 소실에서 **앱이 죽지 않는다**.

## 4. 범위

### 4.1 범위 안 (iOS 1.0)

| 영역 | 내용 |
|---|---|
| **측정** | 스쿼트 자동 카운팅, 자세 판정 7종, 촬영 방향 자동 판별, 준비 자세 점검 5종, 스켈레톤 오버레이, 전/후면 전환, 소리 신호 |
| **기록** | 홈 대시보드(오늘 목표·주간 막대·추정 열량), 운동 결과 리포트, 기록 목록(날짜별 묶음·삭제) |
| **안내** | 온보딩 4쪽 → 측정 준비 시트 → 동작 예시 → 코치마크 (4층) |
| **설정** | 하루 목표, 준비 시간, 신체 정보, 자세 기준 완화, 안내 다시 보기 |
| **저장** | 로컬 DB 4테이블 + `sync_status` (Android Room 스키마와 **같은 모양**) |

### 4.2 범위 밖 (out of scope)

| 제외 | 이유 |
|---|---|
| **서버 동기화 / 로그인** | Android도 미구현. 양쪽이 동시에 들어가야 스키마가 갈리지 않는다 |
| **개발용 화면 2종** (WorkoutLab · Capture) | 데이터 수집은 Android 앱으로 이미 하고 있다. **단, Capture의 CSV/JSONL 포맷은 iOS 검증에 필요하므로 §5 Phase 1의 비교 도구로 별도 구현** |
| **스쿼트 외 종목** | Android와 동일한 스코프 컷 |
| **세트 개념** | rep을 연속으로 센다. Android와 동일 |
| **iPad 전용 레이아웃** | iPhone 세로 우선. iPad는 동작하되 최적화하지 않는다 `[결정 필요]` |
| **watchOS / Apple Health 연동** | 1.0 이후 |

### 4.3 판단 보류 (스택 확정 시 결정)

- 최소 iOS 버전 — 성능·API(특히 `videoRotationAngle`, Swift Concurrency)와 사용자 커버리지의 교환
- 로컬 DB (SQLite 직접 접근 vs SwiftData)
- 추론 런타임 (LiteRT 그대로 vs Core ML 변환)

→ 각 선택지의 비교표는 [03_AOS_iOS_구현차이.md](03_AOS_iOS_구현차이.md)에 있다.

## 5. 릴리스 계획 (게이트 기반)

Android와 같은 방식으로 **날짜가 아니라 완료기준**으로 단계를 나눈다.

```
Phase 0  프로젝트 뼈대 + 모델이 iOS에서 돌아가는가
   └ 완료기준: 같은 사진 1장에서 Android와 키포인트가 ±0.01 안으로 일치한다   ◀ 여기서 막히면 전부 재설계
         ▼
Phase 1  판정 엔진 이식 (:pose-engine → PoseEngine Swift Package)
   └ 완료기준: Android 단위 테스트 전부 Swift로 통과 + 녹화 영상 5개 rep 수 일치 (G1~G3)
         ▼
Phase 2  운동 화면 — 카메라·오버레이·HUD·소리·기준 자세·준비 자세
   └ 완료기준: 실기기에서 한 세트를 끝까지 셀 수 있고, 경고가 Android와 같은 자리에서 뜬다
         ▼
Phase 3  저장·기록·홈·결과 리포트
   └ 완료기준: 스키마가 Android와 같은 모양이고, 0회 세션이 저장되지 않는다
         ▼
Phase 4  안내 4층 · 설정 · 디자인 시스템 마감 · 성능 측정
   └ 완료기준: §3 성공 기준 전부 + TestFlight 배포
```

**Phase 0이 이 프로젝트의 진짜 게이트다.** 모델이 iOS에서 같은 답을 내지 못하면
(전처리 차이·색공간 차이·보간 차이) 그 뒤 모든 단계의 전제가 무너진다. 그래서 화면을 하나도
만들기 전에 **키포인트 비교부터** 한다.

## 6. 비기능 요구사항

| 항목 | 요구 |
|---|---|
| **오프라인** | 네트워크 없이 100% 동작. 네트워크 실패는 절대 운동 흐름을 막지 않는다 |
| **개인정보** | 카메라 프레임은 **기기를 떠나지 않는다**. 영상·이미지를 저장하지 않는다. 저장하는 것은 숫자(키포인트 파생 특징)와 판정 결과뿐 |
| **권한** | 카메라만 요구한다. 거부해도 앱의 기록 기능은 동작한다 |
| **접근성** | 색만으로 상태를 구분하지 않는다(아이콘 병행). 최소 터치 타겟 44pt(iOS HIG). Dynamic Type 대응 `[결정 필요 — 03 문서 §8]` |
| **화면 유지** | 운동 중 화면이 꺼지면 안 된다 ⚠ **Android에 이 처리가 없다** — iOS에서는 자동 잠금이 더 공격적이라 **신규 요구사항으로 추가한다** |
| **다크 테마 고정** | 시스템 라이트/다크를 따르지 않는다. 카메라 오버레이 대비 때문 |
| **언어** | 한국어. 다국어는 1.0 범위 밖 |

| R5 | 판정 로직이 두 저장소로 갈라진다 | 장기적으로 두 앱이 다른 답 | 임계값은 **값 테이블을 공유 포맷(JSON)으로 뽑아 양쪽이 같은 파일을 읽는 방안** 검토 |
| R6 | 측면 데이터 3세션, 의도적 오류 세션 0건 | **Android에서 이미 안고 있는 리스크** | iOS가 새로 만드는 문제가 아니다. 다만 "오류를 잡는가 미검증"을 iOS 리포트 문구에도 동일하게 반영 |

## 8. 측정·검증 도구 (Phase 0에서 먼저 만든다)

판정 동등성은 눈으로 볼 수 없다. 그래서 **비교 장치를 기능보다 먼저 만든다.**

1. **고정 입력 주입기** — 라이브 카메라 대신 녹화 영상/이미지를 같은 파이프라인에 넣는다.
   (Android `:pose-engine`이 `Bitmap`을 받는 이유와 동일한 설계. iOS는 `CVPixelBuffer`)
2. **키포인트 덤프** — 프레임별 26개 좌표를 CSV로 떨군다. Android `CaptureExport`와 **같은 컬럼**.
3. **대조 스크립트** — 두 CSV의 좌표·판정·rep 경계를 비교해 불일치를 표로 낸다.

이 3개가 §3.1 G1~G3의 측정 수단이고, 동시에 회귀 테스트가 된다.

| **기준 자세 (calibration)** | 운동 시작 전 3초간 서 있는 자세를 재서 다리 길이·촬영 방향·정규화 분모를 확정하는 것 |
| **준비 자세 (ready posture)** | 기준 자세 측정을 시작해도 되는지 보는 사전 점검 5종 |
| **rep 단위 판정 / 프레임 단위 판정** | 경고를 매 프레임 낼지, rep이 끝난 뒤 한 번 낼지 |
| **판정 근거 등급** | `DATA_DERIVED`(실측) / `DEFINITION`(정의) / `PROVISIONAL`(잠정) |
| **기준 완화** | 사용자가 켤 수 있는 유일한 판정 영향 설정. 무릎 허용폭과 깊이 얕은 쪽 경계를 넓힌다 |

---

## 10. 이 PRD가 따르는 원칙 (Android에서 가져온 것)

1. **판정보다 근거** — 임계값마다 출처를 붙인다. 근거 없는 숫자는 `PROVISIONAL`로 표시한다.
2. **틀린 답보다 없는 답** — 판정할 근거가 없으면 `nil`을 낸다.
3. **점수 대신 사실** — 종합 점수를 만들지 않는다. "확인한 횟수 / 피드백 횟수"로 센다.
4. **못 본 것을 반드시 말한다** — 판정하지 못한 항목을 결과 화면이 밝힌다.
5. **분모를 의심할 것** — 정규화 분모가 무너지는 자리를 항상 먼저 본다.

이 다섯 줄은 **iOS에서도 그대로 유효하다.** 이식 중에 "일단 돌아가게" 하려고 이 원칙을
어기면, 그 순간 두 앱은 다른 제품이 된다.
