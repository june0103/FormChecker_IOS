# 폼체커 iOS (FormChecker iOS)

카메라로 스쿼트 횟수를 세고, 자세가 어긋나면 화면과 소리로 알려주는 iOS 앱.
**온디바이스 추론**이라 네트워크 없이 동작한다.

[Android 버전](https://github.com/june0103/FormChecker)의 이식이다.
**새 제품이 아니라 같은 제품**이고, 그래서 이 저장소의 1순위 제약은
**"같은 영상을 넣으면 같은 답이 나오는 것"** 이다.

### 지금 보이는 것

시뮬레이터에는 카메라가 없어 **번들 영상**(`squat_demo.mp4`)이 같은 파이프라인으로 들어간다.
실기기에서는 카메라가 자동으로 잡힌다.

- 스켈레톤 오버레이 26점 — **발 6개 포함**
- `기준 자세 재기` → 준비 카운트다운 → 3초 측정 → 촬영 방향 다수결
- ⚠ **데모 영상은 사선 촬영이라 앱이 측정을 거부한다**(`비스듬해요`). 설계대로다 —
  45도에서는 정면·측면 어느 판정도 믿을 수 없다. rep 카운팅까지 보려면 정면이나 측면으로
  찍은 영상이 필요하다
- 앱을 켜면 **오렌지(어긋난 자세) → 라임(교정된 체크)** 모션이 한 번 돌고, 그동안
  포즈 모델을 백그라운드에서 미리 읽는다
- 안내가 **네 층**으로 순서대로 뜬다 — 설치 첫 실행 **온보딩 4쪽** → 첫 운동 전
  **측정 준비 시트** → **동작 예시** → **코치마크 3단계**. 완료 상태는 **버전 값**이라
  안내를 고치면 다시 보여줄 수 있다
- 운동 화면은 전체 화면으로 덮는다 — iOS의 **가장자리 스와이프 백을 막기 위해서**다
  (운동 중 오터치 한 번에 센 횟수가 사라진다)
- 추론 9.7~13.5ms · 30fps (시뮬레이터, 호스트 CPU — **기기 성능이 아니다**)

## 어떻게 판정하나

```
AVCaptureVideoDataOutput ─▶ RTMPose-s Halpe26 (LiteRT, 192×256) ─▶ 키포인트 26개
                                                                     │
                            기준 자세 3초 측정 ◀────────────────────┤  다리 길이·대퇴/정강이 비율,
                            (촬영 방향 다수결)                        │  촬영 방향, 정규화 분모
                                                                     ▼
                                       프레임 특징 ─▶ rep 상태머신 ─▶ 판정
                                       (각도·거리비)  (하강/최저점/상승)  프레임 5종 + rep 2종
```

**왜 Apple Vision이 아닌가** — Vision의 신체 키포인트는 19개이고
**뒤꿈치도 발가락도 없다**. 발 키포인트가 없으면 뒤꿈치 들림과 무릎–발끝 판정을
**아예 계산할 수 없다**. Android가 MoveNet(COCO17)을 기본에서 뺀 것과 같은 이유다.
→ [03 문서 §3.2](docs/03_AOS_iOS_구현차이.md#32-③-apple-vision은-쓸-수-없다-확인함)

## 계획된 구조

```
FormChecker/            앱 타겟 — SwiftUI · AVFoundation · 화면          ✅ Phase 2·3
PoseEngine/             로컬 Swift Package — 추론과 판정                 ✅
  Sources/              26개 파일
  Tests/                316개 테스트
                        의존: Foundation, CoreVideo, CoreGraphics, LiteRT
                        금지: SwiftUI, UIKit, AVFoundation, DB
Storage/                로컬 Swift Package — SQLite(GRDB)와 날짜 경계     ✅ Phase 3
  Tests/                28개 테스트
                        의존: Foundation, GRDB, PoseEngine
                        금지: SwiftUI, UIKit, AVFoundation
```

**날짜 묶는 규칙이 왜 `Storage`에 있나** — 자정과 주 바뀜은 기기 시계로 재현할 수 없다.
`weekWindowOf` / `groupByDay`를 현재 시각과 달력을 인자로 받는 **순수 함수**로 두면
테스트가 그 순간을 만들 수 있고, 홈과 기록이 **같은 함수**를 써서 같은 수를 말한다.

Android가 판정을 `:pose-engine`에 격리한 것과 같은 경계다. 이 경계가 있어야
**기기 없이 단위 테스트**가 돌고, **녹화 영상을 같은 파이프라인에 주입**해 재현 가능한
벤치마크를 돌릴 수 있다.

## 이 저장소의 규칙

Android 저장소에서 반복해서 값을 치르고 얻은 것들이다. **iOS에서도 그대로 유효하다.**

**판정보다 근거** — 임계값마다 출처 등급(`DATA_DERIVED`/`DEFINITION`/`PROVISIONAL`)을 붙이고,
왜 그 값인지·무엇이 미검증인지를 주석에 실측 수치로 남긴다.

**틀린 답보다 없는 답** — 판정할 근거가 없으면 `nil`을 낸다. `0`이나 `false`로 바꾸면
**경고가 영원히 안 뜬다** (Android에서 실제로 겪었다).

**점수 대신 사실** — `form_score`는 항상 `nil`이고 `checked_count`/`warned_count`로 대체한다.

**못 본 것을 반드시 말한다** — 결과 화면이 판정하지 못한 항목을 밝힌다.
말하지 않으면 "피드백 없음"이 "전부 괜찮다"로 읽힌다.

**분모를 의심할 것** — 측면에서 발 길이·어깨폭·힙폭은 원근으로 압축되고,
발목 간격은 두 발이 겹치면 무너진다.

**그리고 iOS에만 있는 규칙 하나** —
> **판정 로직을 iOS에서 먼저 고치지 않는다.** 개선이 필요하다고 판단되면 Android 저장소에
> 먼저 제기하고 **양쪽을 함께** 바꾼다. 한쪽만 고치는 순간 두 앱은 다른 답을 낸다.

## 가장 중요한 게이트

**Phase 0** — 화면을 하나도 만들기 전에, 같은 이미지를 양 플랫폼 엔진에 넣고
**26개 키포인트를 비교**했다. 여기서 어긋나면 임계값 15개의 근거(자체 수집 15세션)가
통째로 무효가 되기 때문이다.

**실제로 ②가 터졌다.** Android `Canvas.drawBitmap(src, null, dst, null)`은 필터링을 하지
않는데(= 최근접), iOS에서 "당연한" 양선형 보간을 썼다면 키포인트가 **최대 0.42** 벌어진 채
크래시도 경고도 없이 넘어갔을 것이다.

| 리샘플링 | Android와의 최대 좌표차 |
|---|---|
| **최근접** (현재 기본값) | **0.0000007** ✅ |
| 양선형 | 0.4166987 ❌ |

→ [측정 결과](docs/05_Phase0_결과.md) · [03 문서 §4](docs/03_AOS_iOS_구현차이.md#4--카메라--추론-전처리-여기가-가장-위험하다)
